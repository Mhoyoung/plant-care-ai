# 개발 순서와 예상 시간

## 현재 위치와 다음 순서

2026-10-19 중간보고와 11월 말까지의 팀 공동 작업은 [팀 운영체계·6단계 간트 계획](PROJECT_PLAN.md)에 정리했습니다.
팀 이름과 역할 배정, 세부 일정은 합의 전 초안이며 최종 발표일은 12월 초 미정입니다.

2026-10-16부터 **12월 초 발표용 Android 시험 설치 앱**을 목표로 모바일 웹 테스트와 병행 준비합니다.
첫 단계는 Android 개발 환경과 식물 목록·상세 조회 연결이며, [Android 작업 순서와 완료 기준](ANDROID_PLAN.md)에 범위를 정리했습니다. APK와 별도 API 서버는 아직 구현 전입니다.
10/19 중간발표는 기존 모바일 웹으로 시연합니다. Android 실기기는 아직 확보 전이므로 초기 개발·설치 확인은 에뮬레이터로 진행합니다.

등록·기록·AI 연동·제안/실행/경과 연결·날씨·비교 화면·팀 정원 영구 저장과 모바일 웹 흐름을 구현했습니다.
현재는 **사용성과 AI 제안 품질 검증 단계**입니다. 기본 기능의 구현 완료와 실제 식물의 관리 효과 검증은 구분합니다.

케어 일정의 등록·수정·취소·실제 완료 기록과 캘린더 내보내기를 구현했습니다. [일정 안내](CARE_SCHEDULES.md)
휴대폰 알림은 우선 캘린더에서 확인합니다. Android 시험 앱에서는 기기 내 예약 알림을 후속 구현 대상으로 검토하고, 서버에서 보내는 푸시는 별도 확장 범위로 둡니다.

1. 세 가상 사례로 기록 반영·조건부 행동·없는 사실을 평가합니다.
2. 팀원이 휴대폰에서 등록·기록·분석 안내를 사용하며 막히는 지점을 남깁니다. [테스트 안내](TEAM_TESTING.md)
3. 실제 식물의 여러 날 관리·사진·경과로 다음 제안을 확인합니다.
4. 발견한 문제를 수정하고 Android 시험 설치와 발표 시연을 준비합니다. 마스코트 디자인과 개인별 서비스·스토어 출시는 이후 범위를 정합니다.

가상 사례 평가와 팀원 사용성 테스트는 실제 식물 확보 전에 병행할 수 있습니다.

## 초기 개발 계획의 예상치

아래 기간은 **초기 설계 단계에서 웹 시제품 구현에 필요한 작업을 추정한 값**입니다.
API 연동 경험, 디버깅 시간, 시험·과제 일정과 작업 분담에 따라 달라집니다.

| 단계 | 완료 조건 | 예상 기간 |
|---|---|---|
| 1. 환경과 기록 흐름 확인 | 설치, 식물 등록, 기록 저장, 재실행 후 조회까지 직접 확인 | 1–2일 |
| 2. 기록 기능 익히고 보완 | 사진·상태 기록, 입력 오류 수정, 기본 화면 정리 | 1–2주 |
| 3. AI 첫 연동 | 현재 상태와 사진을 보내고, 분석 결과를 화면에 표시·저장 | 1–2주 |
| 4. 과거 기록과 결과 반영 | 최근 기록과 이전 제안·실행·경과를 다음 분석에 포함 | 1–2주 |
| 5. 날씨와 시연 준비 | 환경 정보 연동, 오류 처리, 비교 시나리오와 발표 정리 | 1–2주 |

아래 단계의 초기 예상은 **발표 가능한 웹 시제품까지 약 4–8주**였습니다. 현재 남은 기간을 뜻하지 않습니다.
초기 화면이 빨리 만들어져도 데이터 연결, API 오류 처리, 반복 사용 검증에 시간이 필요합니다.

실제 모바일 출시는 별도 작업입니다. 모바일 화면, 로그인, 사용자별 권한, 영구 저장소, 배포 환경,
앱스토어 제출과 운영까지 포함하면 **추가로 약 2–4개월 이상**을 계획해야 합니다.
이 범위는 Android/iOS 지원 범위와 출시 품질에 따라 크게 달라집니다.

## 1단계 · 기록 흐름

현재 코드에서 구현한 단계입니다. 본인 PC에서 실행하고 다음 동작을 이해하는 것이 첫 목표입니다.

- 식물 등록 → 관리 기록 저장 → 식물별 타임라인 조회
- 사진 저장과 재실행 후 데이터 유지
- 같은 식물의 경과 관찰 기록 추가

읽는 순서는 `app.py` → `plant_care/storage.py` → `plant_care/media.py`입니다.
처음에는 관리 종류나 안내 문구 하나를 바꾸고 실행해보는 정도부터 시작하세요.

## 2단계 · 실제 AI 연결

Gemini 호출·분석 저장 코드를 구현하고 모의 API 테스트를 완료했습니다.
개발 환경에서는 예시 기록으로 실제 연결을 확인했습니다. 실제 식물 사진을 사용한 분석 품질 확인은 남아 있습니다.
[무료 구간과 API 키 설정](AI_SETUP.md)을 참고하세요. 현재 모델은 `gemini-3.8-flash`입니다.

- 이미지와 텍스트를 함께 처리하는 기존 AI API를 선택합니다.
- 비밀키는 환경변수나 배포 서비스의 비밀 저장소에 넣습니다.
- `plant_care/ai_context.py`의 입력에 현재 사진과 질문을 붙입니다.
- 응답을 상태 요약, 확인할 사항, 제안 행동으로 나누어 저장합니다.
- 연결 실패, 응답 지연, 응답 형식 오류를 처리합니다.
- 비용을 확인할 수 있도록 실제 호출 횟수를 기록합니다.

사진과 지역 날씨만으로 흙의 수분이나 실내 환경을 확정할 수는 없습니다.
예를 들어 물주기 제안은 사용자가 흙 상태 등을 확인할 수 있는 조건을 함께 제시하도록 설계합니다.

## 3단계 · 관리 결과를 다음 제안에 반영

제안·실행·경과를 연결하는 코드를 구현하고 모의 API와 화면 테스트를 완료했습니다.

- `ai_analyses` (구현): 식물, 분석 시점, 당시 입력·선택 사진, 상태 요약, 제안 행동, 응답 토큰
- `ai_suggestions` (구현): 분석 ID, 제안 순서, 제안 원문과 안정적인 제안 ID
- `care_logs.suggestion_id / link_type` (구현): 제안에 연결한 실제 실행 또는 이후 관찰

제안 하나에 실제 실행 한 건과 이후 상태 관찰 여러 건을 연결합니다.
실행 기록과 관찰 경과를 분리하며, 원래 분석의 입력·응답은 그대로 유지합니다.
관찰한 변화만으로 제안의 효과를 단정하지 않고, 실행 여부와 경과를 구분해 보관합니다.

최근 기록과 이전 제안의 실행·경과를 다음 호출의 입력으로 전달합니다.
현재 관리 기록 최대 30건, 최근 제안 최대 10건과 각 제안의 최근 경과 3건을 전달합니다.
더 오래된 기록을 요약해서 전달하는 기능은 향후 보완합니다.
이 과정은 기존 모델에 문맥을 전달하는 방식으로 시작할 수 있습니다. 초기 단계에 자체 모델 학습은 필요하지 않습니다.
실제 식물을 여러 날 관리하며 분석 품질과 기록 활용 효과를 확인하는 단계는 남아 있습니다.

## 4단계 · 날씨와 비교 평가

- 지역 날씨 연동을 구현했습니다. 식물별 도시 설정, 수동 조회, 분석 당시 기준·조회 시각과 출처를 저장합니다. [사용 안내](WEATHER.md)
- 실외 모델 날씨와 실제 식물이 있는 실내 환경을 구분하며, 날씨 연결 실패 시 사진·기록 분석을 계속합니다.
- 모의 API 테스트로 흐름을 검증했고, 실제 식물에서 제안 품질을 확인하는 단계가 남아 있습니다.
- 같은 사진·상태에 과거 기록을 뺀 버전과 포함한 버전을 수동 비교하는 화면을 구현했습니다. [비교 방법](AI_COMPARISON.md)
- 실제 식물 확보 전에는 가상 사례로 기록 활용을 확인할 수 있습니다. 두 호출·평가·다운로드는 실제 정원과 분리합니다.
- 제안의 구체성, 상황 반영도, 사용자의 이해도를 직접 평가하고 실제 식물 사용과 병행해 검증합니다.
- 시연은 실제 API와 사전에 저장한 예시 결과를 구분해서 설명합니다.

## 모바일 출시를 결정할 때

팀원용 외부 저장소 연결과 전체 정원 백업·이전 기능을 구현했습니다. [설정과 실제 연결 확인](CLOUD_STORAGE.md)
현재는 하나의 팀 정원을 함께 쓰는 방식입니다. 개인별 계정·정원과 역할 분리는 다음 확장 범위입니다.

휴대폰 웹 사용을 우선해 주요 메뉴와 상태 기록 바로가기, 한 열 화면을 구현했습니다. [모바일 흐름](MOBILE_UX.md)
앱스토어 출시를 결정하면 모바일 클라이언트와 Python 저장·AI 처리용 API 서버로 옮기는 방법을 검토합니다.
로그인과 사용자별 데이터 접근, 백업, 장기 보관, 비용 관리가 추가로 필요합니다.
센서, 커뮤니티, 자동 알림은 핵심 관리 흐름을 검증한 다음 우선순위를 정합니다.
